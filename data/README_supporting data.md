# BrewFlow AI — Data Layer Reference

> **⚠️ Important notice**
> This repository does not use proprietary Starbucks internal data. Operational data is simulated for educational prototyping purposes.

---

## 1. Project data overview

BrewFlow AI uses **one real/non-simulated dataset** (the Starbucks public menu) and **five simulated operational datasets** representing a hypothetical Starbucks branch network in San Diego, California.

The simulated data is designed to be internally consistent and realistic for prototype development, but it should not be interpreted as reflecting actual Starbucks operations, financials, or staffing.

---

## 3. How data connects to the workflow

BrewFlow AI is organized around a connected workflow. Here is how each phase maps to the data layer:

**Pre-rush readiness**
The manager dashboard pulls from `daily_sales_forecast.csv` (rush risk and demand level), `staff_schedule.csv` (staffing gaps), and `store_inventory.csv` (low-stock alerts) to generate a briefing before peak hours. The `manager_daily_briefing` automation orchestrates all three sources.

**Customer recommendation**
The `recommendation` skill queries `starbucks_menu_full.csv` for eligible items and cross-references `store_inventory.csv` via `ingredient_mapping.csv` to confirm that required ingredients are available. Active promotions from `promotion_margins.csv` can surface promotional items when relevant.

**Product catalog lookup**
The `product_catalog` skill reads directly from `starbucks_menu_full.csv`. Item name lookups from customer input are resolved through `item_name_mapping.csv` to handle informal names like "iced latte" → "Iced Caffe Latte".

**Order building**
The `order_builder` skill takes customer natural language, resolves item names using `item_name_mapping.csv`, validates size and customization fields against `starbucks_menu_full.csv`, and checks ingredient availability via `ingredient_mapping.csv` + `store_inventory.csv`.

**Order summary**
The `order_summary` skill produces a structured confirmation from the order object built by `order_builder`. It formats the item name, size, milk type, customizations, and estimated price for customer review.

**Inventory monitoring**
The `inventory_monitoring` automation scans `store_inventory.csv` for items at or below `reorder_point`, flags spoilage, and generates alerts. It uses `ingredient_mapping.csv` to associate low-stock ingredients with the drinks they block.

**Staffing gap calculation**
The `staffing_gap_calculator` automation reads `staff_schedule.csv`, computes the gap between `required_staff` and `scheduled_staff`, and flags understaffed windows. It cross-references `daily_sales_forecast.csv` for demand context.

**Rush detection**
The `demand_rush_detection` automation reads `daily_sales_forecast.csv` to identify hours where `demand_level` is High or Very High and where actual orders materially exceeded forecast. It surfaces these windows for manager action.

**Manager daily briefing**
The `manager_daily_briefing` automation aggregates outputs from `demand_rush_detection`, `staffing_gap_calculator`, and `inventory_monitoring` into a single prioritized briefing. It may also reference `promotion_margins.csv` for margin-at-risk items.

## 4. Data quality and alignment notes

### Item name resolution
`item_name_mapping.csv` must be used for all item name resolution when reading from `order_history.csv` or `promotion_margins.csv`. Skills and automations should never perform raw string comparison between operational item names and menu item names without first applying this mapping.

All `canonical_menu_item` values in `item_name_mapping.csv` exactly match an `Item` value in `starbucks_menu_full.csv`, **unless** the row has `match_type = no_match`. This invariant is validated at generation time by `generate_supporting_data.py`.

### Inventory lookup policy
Inventory-aware skills and automations should apply the following lookup order:

1. **Exact match**: look for a `store_inventory.csv` record with the exact `store_id` and `date` of the scenario or request.
2. **Latest prior snapshot**: if no exact-date record exists, use the most recent record for that `store_id` where `date` is on or before the scenario date.

This policy applies to all inventory-aware scenario types, including `morning_rush_readiness`, `inventory_aware_recommendation`, `dairy_free_recommendation`, `low_stock_substitution`, `post_rush_manager_review`, and `promotion_aware_recommendation`.

The `store_inventory.csv` dataset covers 2024-01-02 to 2024-09-06. Scenarios with dates beyond this range (e.g. SCN011 on 2024-10-07) will always fall back to the latest prior snapshot.

### Ingredient term mismatches
`starbucks_menu_full.csv` describes ingredients in narrative form (e.g. "steamed 2% milk", "chai tea concentrate") while `store_inventory.csv` uses shorter normalized names ("2% Milk", "Chai Concentrate"). `ingredient_mapping.csv` bridges this gap and identifies ingredients not tracked in inventory (`inventory_ingredient = not_tracked`), which should be treated as always available.

### Ambiguous item names
A small number of source item names (e.g. "Cake Pop", "Protein Box", "Turkey Sandwich") map to multiple possible menu SKUs. These are flagged with `confidence: medium` or `confidence: low` in `item_name_mapping.csv`. Downstream code should surface a clarifying prompt rather than silently defaulting to one SKU.

### Demo scenario field conventions
`demo_scenarios.csv` uses `N/A` (not blank) for fields that do not apply to a given scenario:
- `customer_prompt = N/A` for all manager-role scenarios
- `manager_context = N/A` for all customer-facing and barista-role scenarios

This prevents blank fields in downstream CSV handling. Note that pandas `read_csv()` parses `N/A` as `NaN` by default; use `keep_default_na=False` when loading this file if you need to preserve `N/A` as a string literal.

### Simulated data scope
All operational datasets are simulated for a hypothetical San Diego branch network (store IDs SD001–SD010). Dates are in calendar year 2024. The data is internally consistent but is not a reflection of actual Starbucks operations.

## 5. Recommended access pattern

Skills and automations should not hard-code file paths. The recommended pattern is:

1. Define a shared configuration object or environment variable that maps logical data names to file paths (e.g. `DATA_PATHS["menu"]`, `DATA_PATHS["inventory"]`).
2. Load data through shared utility functions (e.g. `load_menu()`, `load_inventory(store_id, date)`) rather than calling `pd.read_csv()` inline in skill code.
3. The `load_inventory(store_id, date)` utility should implement the latest-prior-snapshot fallback automatically: first attempt an exact date match, then fall back to `max(date) where date <= requested_date` for that store.
4. Apply `item_name_mapping.csv` as a lookup layer whenever resolving an item name from customer input or operational data.
5. Apply `ingredient_mapping.csv` as a lookup layer before any inventory availability check.

This pattern makes it easy to swap file paths, add caching, or replace CSV files with a database in a future iteration.

## 6. File generation

Supporting files (`item_name_mapping.csv`, `ingredient_mapping.csv`, `demo_scenarios.csv`) are generated by `generate_supporting_data.py`. Run this script from the `data/` directory:

```bash
python3 generate_supporting_data.py
```

The script:
- Prints a row count confirmation for each file
- Validates all `canonical_menu_item` values against `starbucks_menu_full.csv` at generation time and warns on any mismatch
- Reports blank field counts in `demo_scenarios.csv` (expected: 0)
- Does **not** modify the original six datasets
