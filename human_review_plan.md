# Human Review and Control Plan

All review actions (`approve`, `edit`, `reject_rerun`, `escalate`) are wired
to real outcomes in the orchestrator's `review_actions` dict. The
`review_queue` lists each step flagged for human attention with a risk
level and reason. The UI Review Queue tab surfaces the AI-generated
answer, the source docs/tool outputs used, the face-validity verdict, and
four action buttons. Every action appends a `user_review` entry to the
Audit Log so each human decision is traceable.

The seven rows below cover every workflow step where a human can or must
intervene. Rows 4, 5 and 7 are **explicit review/approval points** (the
orchestrator sets `review_required = True` automatically); the others are
advisory but still queue for review when the underlying tool returns a
`needs_review` status.

| # | Process step | What the AI / tool / automation does | What the human does | Human approval required? | What could go wrong | What happens if there is a problem | Evidence the human sees |
|---|---|---|---|---|---|---|---|
| **1** | **Inventory monitoring** | `run_inventory_monitoring` reads `store_inventory.csv` for the requested date, classifies each ingredient as `healthy` / `low_stock` / `overstock` / `unavailable`, counts alerts, and applies the latest-prior snapshot if no exact-date row exists. | Reviews the alert list; checks whether any critical-low item is a high-volume modifier (oat milk, vanilla syrup, espresso). | No — informational, but any item with `unavailable` status auto-queues for review. | Snapshot date is stale (last inventory update was days ago); a "Healthy" status may not reflect today's actual stock. | If snapshot age > 2 days, the orchestrator adds a `stale_data` warning and the face-validity card downgrades to `needs_review`. Human can `reject_rerun` to force a fresh check. | Evidence Center → Tool/Data tab shows snapshot date + each ingredient's stock status; Warnings tab flags stale-data warnings; barista_guidance block in Manager View lists `avoid_ingredients` and `caution_ingredients`. |
| **2** | **Staffing gap calculation** | `run_staffing_gap_calculator` counts unique scheduled employees whose shift covers the requested hour, compares to a baseline required headcount, and classifies as `Understaffed` / `Balanced` / `Overstaffed`. | Reviews the staffing status before the rush; can manually adjust by calling in additional staff or releasing early shift. | No — advisory; manager uses output to decide. | Shift data for the date is missing or the hour falls in a gap between two shifts; "Balanced" at hour 8 may become "Understaffed" at hour 9. | If no staff row matches the requested hour, returns `status: no_data` and flags for human review; the run summary card surfaces `staffing_gap` and `staffing_status`. | Evidence Center → Tool/Data tab shows `scheduled_staff`, `required_staff`, `staffing_gap`, `staffing_status`; Warnings tab shows any data-availability warnings; Manager Readiness card shows the calling-in recommendation. |
| **3** | **Rush-period detection** | `run_demand_rush_detection` aggregates historical order counts for the store/hour from `order_history.csv`, cross-checks `daily_sales_forecast.csv`, classifies demand as `low` / `moderate` / `high` / `very high`, and sets a risk level. | Reviews demand classification and barista guidance; decides whether to open an extra register or pull a barista from food prep. | No — advisory. | History is sparse (new store or unusual date); demand misclassified as `Low` when the forecast says otherwise. | If fewer than 3 historical points exist for the store/hour, emit a `low_sample_size` warning and prefer the forecast value; if the forecast disagrees, the higher demand level wins. | Evidence Center → Tool/Data tab shows `demand_level`, `rush_risk`, `forecast_orders`, `actual_orders`, weather, local events; Manager Readiness card highlights the rush-level pill in barista_guidance. |
| **4** | **Barista drink recommendation** *(explicit review point)* | `search_menu_by_preferences` scores all menu items against parsed customer preferences; `check_inventory_status` cross-references availability for top candidates; RAG retrieves allergen guidance, recommendation guidelines, and rush-hour playbook. | Reviews ranked candidates with their scores and reason codes; checks that allergy flags are visible; **must approve before the recommendation is communicated to the customer.** | **Yes** — `review_required = True` is always set on the recommendation step. | Top candidate is out of stock; allergen missed because the ingredient is `not_tracked`; recommendation ignores an active promotion that would reduce cost. | If the top item is unavailable, the next in-stock alternative is surfaced; allergen detection uses the menu CSV directly (not just inventory), so `not_tracked` items are still checked; active promotions are included in evidence for manual verification. | Evidence Center → Tool/Data tab shows candidate ranking with scores and reason codes; RAG tab shows the 3+ docs retrieved (titles + snippets + matched terms); Review Queue surfaces a `recommendation_candidates` item with Approve / Edit / Reject + Rerun / Escalate buttons; Face Validity card shows status, anchors, supporting reasons, concerns. |
| **5** | **Order building and validation** *(explicit review point)* | `build_and_validate_order` parses the raw text with regex (size / temperature / milk / syrups / toppings / quantity), resolves the item via the 4-step mapping + menu-search fallback, checks inventory for parsed ingredients, and runs allergy/medical-language detection. | Reviews parsed order fields before submission; corrects misidentified item, wrong size, or missing modifier; **approves or edits before the order is finalized.** | **Yes** — when `item_resolved = False`, `missing_fields` is non-empty, or any ingredient is `unavailable`. | "Iced venti oat latte" parses correctly but "venti soy dirty chai" mis-resolves to Chai Tea Latte (misses the "dirty" espresso shot); size token stripped too aggressively leaves an unresolvable name. | Unresolved fields populate `missing_fields`; orchestrator pauses with `review_required = True`; the Review Queue lists the raw order text, the structured order so far, the best match found, and a follow-up question. | Order Builder output card shows `structured_order` (item, size, temp, milk, syrups, toppings, customizations), `missing_fields` list (red banner), `follow_up_question`, prep notes; Review Queue surfaces `order_missing_fields` and/or `order_allergy_review` with the relevant action button. |
| **6** | **Order summary and confirmation** | `order_summary` skill generates a customer-facing confirmation and a barista prep note from validated order fields; RAG retrieves `order_confirmation_standard.md` and `drink_quality_consistency_sop.md` to anchor the wording and the "prepare individually" rule. | Reviews the confirmation message for clarity; checks that the prep note matches what was ordered before reading it back to the customer. | No — if the order was approved in step 5, the summary is auto-generated; manager can override. | Summary states wrong milk type because a resolved item-name default differs from the modifier parsed in step 5; prep note omits a requested syrup stored as a customization note. | Order summary renders every field in `customizations` as a line in the prep note; if the RAG `order_confirmation_standard.md` doc score is 0, a `weak_evidence` warning is added and a final human sign-off is required. | Order Builder output card shows prep_notes (including the "prepare individually" line), customer-facing confirmation text; Audit Log records the `workflow_completed` entry and any human Approve / Edit action. |
| **7** | **Evidence quality + face-validity gate** *(explicit review point)* | `build_evidence_package` scores all evidence across the run (RAG docs, tool outputs, inventory data) on a 0–1 scale; `generate_face_validity_check` produces a deterministic plausibility verdict with status, confidence, anchors, supporting reasons, and concerns. | Reviews the face-validity badge and evidence quality score; decides whether to approve the run or reject and re-run. | **Yes** — when quality score < 0.4, status is `weak`, or status is `needs_review` with `recommended_action = escalate`. | A run with no RAG docs (all scores = 0) and only one tool output still appears to succeed; or a benign request gets falsely escalated because RAG content contained an allergen-related word. | The face-validity card shows specific concerns inline (no opaque summary); benign-request false escalation was fixed earlier in the project by scanning only safe signal sources (user_input, warnings, review_queue labels). Human can `reject_rerun` to broaden the query or `escalate` to a senior manager. | Evidence Center → Quality + Face Validity sub-tab shows score + label + recommendation; the Face Validity card on every workflow output shows status colour, confidence, anchors as chips, supporting reasons, concerns, and recommended action. |

## Mapping to the UI

| Review action button | Where it appears | What it records | What it does next |
|---|---|---|---|
| **Approve** | Review Queue cards + workflow-level review section | `user_review · approve · <target>` in Audit Log; card gets green left border + "approved" pill | Workflow result stands as final |
| **Edit** | Same locations | Opens modal for a free-text note; records `user_review · edit · <target> · <note>`; card gets blue left border | Manager edits the AI output before delivery |
| **Reject + Rerun** | Same locations | Records `user_review · reject_rerun · <target>`; card gets red left border | Run the workflow again with revised inputs |
| **Escalate** | Same locations | Opens modal for an escalation reason; records `user_review · escalate · <target> · <reason>`; card gets amber left border | Routed to a senior manager / off-tool follow-up |

## Notes

- For **customer-facing workflows** (barista recommendation, order builder, order summary, full workflow), `status = needs_review` is the *designed* state, not a failure. Human approval is part of the process and is never bypassed.
- Every review-queue item carries enough context (reason, follow-up question if any, candidate alternatives, face-validity verdict) for a person to act on it without re-reading the original input.
- Review actions are kept in an in-process audit list (no database). A production deployment would persist these for full traceability.
