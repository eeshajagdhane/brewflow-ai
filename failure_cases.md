# Predicted Failure Cases

This is the predicted-failure register for BrewFlow AI. Each row names a
realistic failure mode, explains why it could happen, and documents how
the current process handles it. The "Covered by tests?" column points to
the specific local test that exercises the failure path or, where no
direct test exists, lists the test class that would catch a regression.

All operational data referenced below is the **simulated** Starbucks
prototype data in `data/raw/` — no proprietary Starbucks data is used.

| **FC-01** | **Item name not resolved** | A customer orders something like "venti soy dirty chai". | **FC-02** | **Stale inventory snapshot** | No inventory record exists for the exact requested date; the latest prior snapshot is from 2+ days ago; stock levels have changed since then. | Barista recommends a drink whose key ingredient ran out yesterday; customer disappointment and wasted prep time; potential refunds. | Evidence Center → Tool/Data tab shows a snapshot date different from the requested date; `latest prior` text appears in the warning; the inventory status badge shows the actual snapshot date. | `get_inventory_snapshot()` uses the latest-prior fallback and records the actual snapshot date in evidence; a `stale_data` warning is added; the face-validity card flags "Inventory evidence uses a latest-prior snapshot rather than exact same-day data." in concerns. | ✅ Tested by `tests/test_mcp_tools.py::test_check_inventory_latest_prior_fallback`; the warning surfaces in `tests/test_face_validity.py` via the safe-signal scan. |

| **FC-05** | **Recommendation ignores active promotion** | The promotion-scoring step in `search_menu_by_preferences` matches promotions by exact store + date + item name. | **FC-06** | **Order validation passes but prep note is incomplete** | The order parser correctly resolves the item and inventory is fine, but a paid customization (e.g. "extra shot") is captured in the free-text `customizations` field rather than a structured option. | **FC-07** | **Evidence quality score inflated by low-value matches** | `evidence_quality_score` awards points for each retrieved RAG doc and tool output present, regardless of relevance. A workflow that retrieves three tangentially-related docs can score 0.7+ (green) even though none address the key question. | A reviewer trusts the green score and approves; a poorly-supported recommendation goes through as if well-evidenced; bad recommendation reaches the customer. | Evidence quality score shows green but the matched terms / snippets in the RAG sub-tab are clearly off-topic on close reading. | The face-validity card shows the score alongside the supporting reasons and concerns; the UI Evidence Center surfaces every retrieved doc with its matched_terms chips so reviewers can verify relevance directly rather than trusting the score alone. | ✅ Schema covered by `tests/test_face_validity.py` (verifies the quality fields exist + reasons/concerns populate). | **FC-08** | **False allergy escalation from RAG content** | The face-validity detector once stringified `final_output` to scan for allergy keywords. `dietary_allergen_guidance.md` always surfaces in dairy-free RAG retrieval, and the word "allergen" leaked into the scan, falsely escalating benign requests to `recommended_action = escalate`. | Baristas see an "Escalate to allergen review" badge on completely benign requests (e.g. "hot caffeinated drink"), eroding trust in the safety routing and creating alert fatigue that masks real allergy cases. | The UI shows a yellow `needs_review/escalate` face-validity card with a concern mentioning allergy/medical-sensitive language, but the customer never typed any allergy-related words. | **Fixed during development**: `_safe_signal_text()` in `utils/face_validity.py` now scans only `user_input`, `warnings`, and `review_queue` item labels/reasons. Real-allergy detection is verified by `test_orchestrator_allergy_request_escalates`. |

## Failure modes that need future testing

The current local test suite (95 cases) covers most failure paths above
with a direct or near-direct assertion. The cases below are honest gaps
that a DeepEval / user-study cycle would close:

- **FC-01 fuzzy resolution beyond regex**: end-to-end paraphrased orders ("oat caramel macc grande iced") versus canonical resolution.
- **FC-04 forecast-vs-history disagreement**: a holiday or one-off event where forecast and history sharply diverge.
- **FC-05 promotion-name mismatch**: same item referenced with a different name across CSVs.
- **FC-06 customization drop**: a paid extra captured in free-text rather than structured.
- **FC-07 semantic relevance of RAG matches**: LLM-judge evaluation that the retrieved doc actually answers the question.

These gaps are also documented in `test_report.md` under "What would improve with more time".
